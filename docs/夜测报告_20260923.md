## 三、P1 发现：loopMIDI 端口改名断开工程时钟路由（演出前必须处理）

**现象**：
1. 每次打开任何工程都弹「未找到端口」（程序自动回车放行，工程能正常开）。
2. 播放键发出后（`intro` 与 曾验证过时钟的 `優しい彗星` 各测 20–25s），`VJ Automation`、
   `Keyboard Automation`、`Rubix24` 三个输入口 **均无任何时钟/音符事件**（计数全 0）。
3. 走带跟随与播完自动推进依赖该时钟 → 真机断链（离线状态机测试全覆盖且通过，
   问题只在时钟数据源）。

**根因**：loopMIDI 端口已改名为 `VJ Automation` / `Keyboard Automation`（dist 配置
`vjPortHint` 记录了新名），但 Cubase 工程内引用的 MIDI 端口按**名字**绑定，仍指旧名
（「未找到端口」弹窗互证）。

**修复方案（三选一，演出前验证）**：
1. 在 loopMIDI 里新建一个名为 `loopMIDI Port` 的端口（保留现有两端口），让旧名引用
   重新有效，然后在各工程把时钟目的地指向它；
2. 在每个用于演出的工程里，把 工程同步设置→MIDI 时钟输出目的地 改为 `VJ Automation`；
3. 把端口名改回旧名，并同步 `config.json` 的 `vjPortHint`。

**修复后的验证方法**：`py -u night_test.py advance`（F1–F7 全套：播放/停止/暂停/继续
键序 + 两段式自动推进全周期 + 手动停不推进 + panic）。本夜这些用例因无时钟数据被
SKIP，状态机逻辑已由 `test_bridge.py` 离线覆盖。

## 四、环境发现（非代码 bug）

1. **根目录 `config.json` 落后于部署**：缺 `vjPortHint`/`kbPortHint`。按源码直接跑
   `python setlist_gui.py` 时 VJ 监听会找默认名 `loopMIDI Port`（已不存在）→ 显示
   「未找到」。测试时已临时补齐（备份在手，测试后恢复原样）。建议：把 dist 的完整
   config 结构同步回根目录。
2. **`ensure_loopmidi` 在改名环境下误判**：它等待出现 `PORT_HINT`（默认 `loopMIDI
   Port`）名端口，改名后永远等不到 → 重复拉起 loopMIDI（单实例，无害）并报错。
   15 秒等待窗口对冷启动（实测 ~17s）也偏紧。建议：等待窗口放宽到 30s，且 loopMIDI
   是否在跑改用进程判断而非端口名。
3. **13 版本保存工程的窗口标题跨版本规则**未在真机触发（本夜打开的工程标题均为
   `Cubase Pro 工程 - 名`）；标题解析规则已有单元覆盖（`test_bridge`）。
4. **恢复语义**：崩溃重启恢复 `cur` 的前提是开着的工程**在播放列表里**；不在列表时
   NOW 横幅仍正确显示实际工程（本夜实测），但指针无从恢复。符合设计，演出前把
   当晚曲目排进播放列表即可。

## 六、稳定性浸泡（95 分钟，23:55–01:31）

**负载**：真实 App 连续运行 95 分钟（全部真实服务）；独立注入器每 28s 一轮
（音符 60 起播视频→3s 后音符 90 熄屏→5 秒 25Hz 时钟突发）；每 15 分钟一次真实
Cubase 切歌。健康监控每 60s 一查（进程/心跳/日志增长/crash.log）。

**结果**：172 轮注入全部完成、App 心跳全程新鲜（≤5s）、crash.log 全程 0 字节、
OBS 视频随音符反复起播/熄屏、走带跟随状态机随时钟突发反复翻转，**无一次假死或
崩溃**。12 次「日志零增长」ALARM 全部对账为负载注入器被切换等待阻塞、暂停注入
的窗口（App 本身无异常）。

**浸泡暴露的 P1 发现（本夜最有价值的结果）**：

切歌手交（CLI 单实例转交）在浸泡条件下会**排队迟到执行**——00:10 发出的
TAIDADA 打开请求直到 ~00:29 才落地；此后每次切歌的"实际打开"落后请求 1-2 个
周期（120s 超时放弃 vs 请求最终被执行），并在无人操作时改变当前工程。对比：
E 阶段干净状态下同路径 10/10 次恒定 5.0s；浸泡结束后的回归中，积压在数轮内
自愈排空、回到 5.5s 稳定（耗时序列 [120.1, 46.5, 47.5, 5.5×7]）。

- **App 侧表现完全正确**：NOW 横幅以真实窗口为准，实测出现红警
  「intro（预期優しい彗星，不一致！）」——不一致告警在真实故障条件下工作。
- **风险模式**：演出中若某次切换超时失败，稍后工程可能"自己"切走（迟到请求落地）。
- **建议**（按代价从小到大）：
  1. 切换超时失败后，控制线程不要立刻放弃：再补发一次手交并再等一轮
     （现有"放行模态后补发一次"只覆盖弹窗场景）；
  2. 超时后持续观察 30–60s：若出现**非所求**工程窗口（迟到请求落地），自动
     WM_CLOSE 关掉并重新请求用户所选，保证"界面当前项=真实工程"；
  3. 排查根因：空框架「Cubase Pro」与 Hub 并存时转交被推迟——在 `_open` 里
     把该状态也纳入"先清理再转交"的特判（现有代码只处理"只有空框架"）。

浸泡末态 result：监控栏三绿、cur 保持、素材库 66 首（5 首时长未知待手填）、
NOW 红警正确。
