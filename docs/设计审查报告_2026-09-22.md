# 工程播放台 设计审查报告（PM 视角）

- **日期**：2026-09-22
- **审查对象**：工程播放台（setlist_gui.py 及支撑模块，约 4000 行，dist\工程播放台）
- **审查方法**：通读全部源码（setlist_gui / cubase_ctrl / advance / kbd_auto / pedal / obs_ctrl / midi_bridge / cpr_meta / dpi），并用打桩方式离线渲染真实界面截图做量化分析（无外部副作用），结合八轮需求迭代的来龙去脉。
- **截图量化证据**：窗口 960×780；主色 `#F0F0F0` 原生灰占 52%、白色 29.5%，平均亮度 234/255；文字 9pt，列表行距约 17px。

**总体结论**：这个项目的**工程质量高于绝大多数同规模个人项目**——跨线程纪律、超时重试、原子写入、损坏降级、"轮询绝不死"护栏，都是对着真实翻车修出来的。但它现在是"工程师的控制台"，还不是"演出者的舞台工具"：**信息层级倒挂、防误触缺失、舞台可读性不足**是三大产品级短板；稳定性方面，框架（tkinter）不是瓶颈，真正的风险在单进程全家桶和对 Cubase 的 UI 自动化通道上。

---

## 一、功能运行逻辑 vs 用户直觉

### ✓ 符合直觉、做得好的

- **开始 = 回零从头播**：演出场景下这是正确语义（不是"继续播放"），按钮文案与行为一致。
- **无工程时按「开始」自动加载播放列表当前项并播放**（setlist_gui.py `_transport`）——用户不必想"我要先切歌再播放"，程序替他想了，这是四轮修复里最有价值的一条。
- **切换忙时手动请求排队（只留最后一次）、自动推进不排队**——既不丢用户意图，又避免自动逻辑插队添乱。
- **双击当前项不重载、移除当前播放项时指针顺移并留日志、上一首在开头只记日志**——边界行为都有交代。
- **踩钉"学习"流程**（点学习→踩一下→完成）是行业标准的 MIDI learn 范式，8 秒超时+去抖设计周到。

### △ 有摩擦、不够自动化的

1. **时长输入框的预显示文字是个陷阱**（`_update_dur_target` / `_set_duration`）：输入框预填「自动时长/未知」，用户点进去直接打字会变成"自动时长213"，然后报格式错误，提示"请清空后输入"。演出前的高压时刻，这就是"莫名其妙的卡点"。修法很便宜：输入框获得焦点时全选（`Entry.select_range(0, 'end')`），打字即覆盖。
2. **配置键盘自动化必须先把歌加进播放列表**（`_open_kbd`）：映射文件本来就存在工程文件夹里，从素材库直接选中一首就能配置才是直觉预期。现在的限制是数据模型（"当前工程"）泄漏到了编辑流程里。
3. **编排效率低**：加入只能单曲双击（Listbox 默认单选），66 首库里拼一场 20 首的歌单要点 40 次以上；排顺序靠「上移/下移」逐格挪，排错一首要挪 N 次。无搜索框，找歌靠肉眼+滚动。演出软件的编排是赛前高频操作，这里值得一次专门的效率改造（多选加入、搜索过滤、整队加入）。
4. **「暂停/继续」不随状态启停**：暂停键在停止态按下会触发"NUM0 跳回上次起播位置"（M0 项），继续键在播放中按下会踩空格直接停走带。按钮应该状态化：播放中禁用「继续」、停止态禁用「暂停」。
5. **自动推进的承重墙是时长数据，但数据错了会变成事故而非失效**：时长偏短 = 提前停止走带切歌（演出中掐掉尾奏）；时长未知 = 静默不推进。现在有剩余时间显示和三态着色（好），但缺最后一道保险——例如"程序接管停止走带"前在日志给红字强提示（现在有事件日志但不够醒目），或首场使用时人工核验一遍各曲时长。**且两段式自动推进至今未真机验证（M0），这是演出前必须闭环的项**。

### ✗ 违反直觉或高危的

6. **双击播放列表 = 立即切歌，无任何确认**（`_on_pl_dbl` → `_switch`）：这一下会关闭当前工程（自动保存）并打开新工程——**演出中手抖双击错行，当前曲目当场死掉，无法挽回**。双击是列表上最容易误触的手势，却绑定了全软件破坏性最强的动作。建议：走带活跃（时钟在跳）时双击必须确认，或改为"单击选中 + 显式「切换」按钮"。
7. **「退出」无确认，且和演出按钮同排**：误点一下整个控制台消失——Cubase 声音还在，但视频、音色切换、踩钉全部失联，黑着脸找图标重启。清空播放列表都有二次确认，退出反而没有，防护等级倒挂。
8. **全停（panic）没有任何屏幕入口**：主界面的全停按钮被移除后，panic 只剩踩钉绑定路径——而踩钉绑定本身还是 M0 未验证状态。如果现场踩钉没绑成或没带，"所有工程窗口发停止"这个最后保险手段在软件里够不着。

## 二、前端 UI 设计

**做得好的**：上下两段的分区理性（数据→监控→操作）；按钮随标蓝启停（affordance 到位）；状态语义色绿/黄/红贯穿监控栏和列表三态着色；日志清空按钮内嵌右上不占独立空间。这是一套**信息组织合格**的界面。

**问题（按对演出的影响排序）**：

1. **信息层级倒挂——最核心的 UI 问题**。演出者最需要的三样东西：「现在放哪首、下一首是什么、还剩多久」，被压缩在底部"播放信息"组的一个 9pt 小标签里，而且**"下一首"根本没有显示**。与此同时，诊断性质的日志栏与歌单列表平分了所有伸展空间。正确的层级应该是：顶部一条 NOW/NEXT 大字横幅（歌名 20pt 以上+倒计时），全窗最醒目；日志固定高度不参与伸展。
2. **舞台可读性不足**。原生浅灰底 + 9pt 字，在暗场、距离一米、余光扫视的真实使用场景下不可读。演出软件的行业惯例是深色底、高对比、大字号（参考 Ableton、QLab、vMix 的演出视图）。tkinter 做深色主题成本不高（ttk `clam` 主题+统一配色），哪怕只把 NOW/NEXT 条和「开始」按钮做成大字深色，体验就换一档。
3. **「开始」没有视觉权重**：六个等大按钮并排，全软件最高频、最重要的动作淹没在序列里。应该加大加粗加色（绿色系），并与其他走带键拉开间距分组。
4. **监控栏两框不等高**（VJ 4 项 2×2 vs 键盘 3 项单列），底边不齐；VJ 标签列宽 12、键盘列宽 8，左边线参差。
5. 细节项：窗口无 minsize（可以拖到畸变）；无程序图标；子窗口（键盘自动化/踩钉）是非模态 Toplevel，被主窗盖住后没有再置前的手段（`lift()` 只在打开时调一次）。

**美观度结论**：布局是"讲道理"的，但视觉是"未设计"的——默认控件、默认字体、默认灰，没有任何主题化痕迹。以工具软件标准约 70 分，以演出软件标准不及格。**建议做一次专门的"演出视图"改造（深色+大字+NOW/NEXT），它的降错价值高于任何新功能。**

## 三、技术栈与稳定性（演出软件视角）

### 先直接回答"tkinter 够不够"：框架不是短板，可以继续用

- 本项目的稳定性瓶颈根本不在 UI 渲染，而在**对 Cubase 的控制通道是 UI 自动化**（窗口标题匹配、仿人按键、前台焦点）——这是产品形态决定的天花板，换任何前端框架都不会变好。代码里已经选了实测最稳的路径（CLI 单实例转交打开、WM_CLOSE 关闭、超时+补发+排队+弹窗排除法），防御密度很高。
- 纯标准库 + onedir exe 的依赖面最小（本机 python-rtmidi import 即崩的教训证明了这点）；对比 Electron/CEF 的体积和 GPU 崩溃面、Qt 的重量，对这个单机单用户工具，tkinter 是合理选择。
- 单线程 Tk + 跨线程队列的纪律执行得好：winmm 回调只记账、重活全在后台线程、`_tick`/`_watch` 有"绝不静默死"的护栏——这是很多商业软件都做不到的。

### 真正的稳定性风险（按优先级）

1. **单进程全家桶**：GUI、VJ 视频桥、键盘自动化、踩钉、Cubase 控制、OBS 客户端全部在一个进程里。ctypes 回调和 SendInput 是原生代码，任何一处崩 = 整场联动全灭（视频停在最后一帧、音色不切），恢复靠人工重启。现有恢复设计（重启后按 Cubase 窗口标题还原当前曲目、OBS 断线重连、踩钉热插拔重连）不错，但"死一次"本身没有兜底。**最低成本的补法不是重构，是两件事**：① `faulthandler.enable()` 把崩溃栈落盘——noconsole exe 崩了现在连尸检都没有；② 评估把 VJ 链路交回独立的「MIDI视频桥.exe」跑（仓库现成），播放台死掉至少视频不受影响，代价是两处配置。
2. **UI 回调无统一异常护栏**：`_tick`/`_watch` 修过了，但按钮回调没有——例如 `_redict` 里 `song` 为 None 时直接 `AttributeError`（noconsole 下静默吞掉，按钮"点了没反应"）。一行 `root.report_callback_exception = ...` 把异常转投日志框即可闭环，建议立即加。
3. **走带 = 抢焦点 + 硬编码键位**：每次走带都要把 Cubase 抢到前台发键（这是 Cubase 无控制 API 下的现实约束），发键瞬间操作者的任何输入都可能干扰；键位假设"本机默认"，Cubase 偏好一改就静默失效。旧仓库的 keys.py 可配置键位能力随重构丢了，建议在 config.json 恢复键位映射，至少写进文档。
4. **启动串行、一票否决**：`_startup` 里 `ensure_loopmidi()` 失败即 `sys.exit`，后面的 OBS、Cubase 控制、踩钉全部不启动——GUI 活着但基本残废。loopMIDI 通常能自动拉起所以触发概率低，但按"逐项独立降级"的原则，这里应该继续起其余服务+红字提示，而不是整体放弃。
5. 小尾巴：`_probe_durations`（后台线程）与主线程同时序列化 playlist.json 的窗口期可能抛 `RuntimeError`（dict 并发修改），而 `_persist` 只捕 `ValueError/OSError`——把 RuntimeError 加进捕获即可。

### "不流畅卡点"清单（汇总）

- 时长框打字前必须手动清空；
- 配置音色必须先入播放列表；
- 排歌序是逐格上移；
- 找歌无搜索；
- 误触双击切歌无挽回；
- panic 无屏幕入口；
- 退出无确认。

## 四、其它审查维度（PM 自行补充）

- **验证债是最大的隐性风险**：两段式自动推进、走带键序实际行为、踩钉学习链路、JUNO 设备 ID 等全部是 M0 未验证状态，而**这份清单只存在于开发记忆里，仓库中没有任何载体**（无 TODO.md/KNOWN_ISSUES）。演出是不可重来的交付场景，建议把 M0 清单固化进仓库，并配一页 runbook：赛前自检步骤（`test_bridge.py`/`e2e_test.py` 分阶段跑）、现场故障恢复路径（Cubase 卡弹窗怎么办、OBS 崩了怎么办、播放台死了怎么最快恢复）。
- **README 已过时**：还是"MIDI 视频桥"时代的文档，主程序"工程播放台"（现在事实上的演出入口）零文档——config 字段、双 exe 关系、踩钉/键盘自动化用法都没有。哪怕只有你自己用，三个月后的自己也是新用户。
- **注释与实测矛盾**：cpr_meta.py 文档串写"Cubase 播放到右定位条自动停止"，而 advance.py 的两段式前提是"播到头不会自己停"——后者是实测结论，前者是陈旧假设，留着会误导未来维护。

## 优先级建议

| 级别 | 事项 | 理由 |
|---|---|---|
| **P0（演出安全）** | NOW/NEXT 大字条+倒计时；退出确认+播放中双击切歌确认；恢复 panic 屏幕入口；`report_callback_exception`+faulthandler；M0 真机验证 | 直接决定翻车概率与翻车后的恢复速度 |
| **P1（流畅度）** | 时长框 focus 全选；库搜索+多选加入；键盘自动化支持素材库选中；走带按钮状态化启停；深色大字主题 | 消除"莫名其妙的卡点" |
| **P2（架构）** | VJ 链路进程隔离/看门狗；键位可配置；M0 清单+runbook+README 入库 | 降低单点崩溃面，固化知识 |

**一句话收尾**：这个项目的防御性工程已经是 90 分，信息设计和防误触设计大约 50 分——接下来最值钱的投入不是更稳的代码，而是把"演出者此刻需要什么"放到屏幕最大、最亮的位置，并给每一个不可逆动作加一道闸。
