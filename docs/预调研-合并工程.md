# 预调研：合并工程功能（多 .cpr 拼接）

日期：2026-10-27（第二轮探针实证已并入）｜ 性质：远期功能预调查，未写任何功能代码（探针在 `out/probe_cpr_*.py`，全部只读）。证据见各节。

---

## 一、结论（TL;DR）

**可行，但技术前提和最初设想不同。**

1. **.cpr 已经不是文本。** Cubase 13 起 .cpr 改为二进制容器（RIFX），C14/15 换为 RIF2 变体。本机 Documents 下 63 个工程全部是 Cubase 15.0.5 写入的 RIF2 二进制，**没有一份是 XML**。"CPR 是可解读文本"的印象来自 Cubase 12 及更早的 XML 时代。
2. **但格式是自描述的，且已在本机完成主干逆向。** 第二轮探针已解明：容器布局、术语记录编码、值类型标签系统、对象嵌套规则、拍号/速度/媒体属性/轨道结构的具体编码（见第五节）。整文件语法还剩 MIDI 事件区等长尾，属于 POC 工作量而非可行性风险。
3. **工程库已按模板统一，实测成立。** 全库 86 个工程中 59 个轨道序列与模板逐类一致（3~4 条轨道 + 系统轨），合并可以做"同名轨道内容顺延"。
4. **推荐路线：读端逆向（已完成主干）→ 输出 XML 时代格式（≤C12 .cpr）→ Cubase 15 官方兼容打开转换 →（可全自动）关闭即保存转 RIF2。** 该路线把风险最高的"二进制写入器"整体消掉。
5. **工作量预估：POC 到可用原型约 2~4 周全职当量**。设计案见 `docs/设计-合并工程.md`。

## 二、格式实证（本机取证）

### 2.1 版本史与容器

| 时代 | 容器 | 证据 |
|---|---|---|
| Cubase 12 及更早 | 纯 XML 文本（`<?xml ...?><CubaseDocument>`） | 社区共识、大量旧文档（本机无样本） |
| Cubase 13 | `RIFF` + 4 字节大端 size，内嵌 `NUNDROOT` 节点流 | 本机 C13 模板 `Standard program.cpr`，写明 `Version 13.0.40 / May 13 2024 / WIN64 / UTF-8 / zh` |
| Cubase 14/15 | `RIF2` + 8 字节小端 size，同样 `NUNDROOT` | 本机 C15 模板与全部 63 个工程，`Version 15.0.5 / Oct 20 2025` |

（C13 AppData 残留的 25 个 RIFX 是旧模板/备份；用户工程已全部在 C15 重存。）

### 2.2 内部结构：自描述对象流

NUNDROOT 后是嵌套的节点流。从模板文件直接可读出（抽查示例）：

- **类名**：`MFolderTrack`、`MDeviceTrack`、`MAudioTrack`、`MMidiTrack`、`MAutomationTrack`、`MTempoTrack`、`MSignatureTrack`、`MMarkerTrack`；事件类 `MAudioEvent`、`MMidiTrackEvent`、`MTempoTrackEvent`、`MSignatureTrackEvent`、`MMarkerTrackEvent`；引用类 `PAudioClip`、`PMediaDescriptor`、`CmIDLink`、`CmArray`。
- **字段名**：`Flags / Start / Length / Bar / Numerator / Denominator / Position`（拍号事件全字段）、`Name / Value / Type / State / Slot / SlotType / BypassTag / RuntimeID / GUID / Bus UID / Bus Type`。
- **字符串**：UTF-8 明文，含中文（"无效果"、"输入/输出"、"立体声"、"垃圾桶"、"Wave 文件"）。
- **媒体引用**：绝对路径 + GUID 双重定位，如 `C:\Users\XKZ\Documents\Cubase Projects\010 Production\Orange Sapphire\Audio\1.wav` + `{58196232ABF241D9BCF703711E992579}`，另有 `OrigPath`（原始入库路径）和 time-stretch 算法预设字段。
- **插件状态**：VST3 状态以二进制块内嵌（含第三方插件的 `JUCEPrivateData` XML 片段——C15 文件里唯一的 `<?xml` 就是它，工程本体没有 XML）。
- **交叉引用**：`RuntimeID`（小整数句柄，通道/插件槽引用）与 `CmIDLink`（ID 关联）承担内部引用，合并重组时需要重排。

模板文件本身是从工程另存的，池里残留 `TEST`、`Orange Sapphire` 等工程的媒体路径（"脏模板"）——做媒体处理时要注意模板残留引用，不影响合并方案。

### 2.3 C15 对旧格式的兼容

- `Cubase15.exe` 内检出 XML 时代类名残留（`MidiTrack`×12、`MarkerTrack`×11、`AudioPart`×4 等）与 `obj class`×810（XML 序列化标签语法），说明旧 XML 处理机器仍在。
- 论坛实证（2024-10）：C13 直接打开 Cubase 10.5（XML 时代）工程成功；"C13 打不开 C12 文件"的帖子属孤例（重存即好）。
- 结论：**C15 读 XML 时代工程是产品级兼容行为**，可以作为产物的落点。

### 2.4 社区逆向现状

- 旧 XML 时代：格式被广泛理解，StackOverflow 有专门讨论。
- SX2 时代二进制：[omeriko9/Cubase-Project-File-Reverse-Engineering](https://github.com/omeriko9/Cubase-Project-File-Reverse-Engineering) 解过 VST Mixer 结构（思路可参考，格式已换代）。
- **C13/15 的 NUNDROOT/RIF2：没有任何公开解析器或逆向文档**（搜索无果）。这条路是无人区，但正因为格式自描述，属于"无人走过但路本身可见"的情况。

## 三、本机工程库现状（合并的输入端）

- 63 个工程全部 RIF2 / 15.0.5；单文件 0.9~1.9 MB。
- 模板 `Standard Vo Effect.cpr`（1.25 MB，10-22 存）轨道构成：**1 folder + 2 音频轨 + 2 MIDI 轨 + 自动化/速度/拍号/标记/设备轨各 1**。
- 结构同一性初验（模板 vs SOUL SOLDIER vs Fly Me To The Moon）：`MidiTrack` 2/2/2，`MTempoTrackEvent` 1/1/1，`MSignatureTrackEvent` 1/1/1，`MFolderTrack` 1/1/1，`MGroupEvent` 1/1/1，`Bus UID` 51/53/51——**已统一工程与模板同构**，且同一性可以用二进制内标记计数做程序化校验。
- 含义：合并可以做**同名轨道顺延**（歌 A 的"音轨 1"内容接在歌 B 的"音轨 1"内容后面，全曲共用一套轨道），而不是垂直堆叠两套轨道集合。工程最终保持模板的轨道数量，混音架构唯一，正好配合演出场景。

## 四、合并需要解决的技术问题清单

| # | 问题 | 难度 | 方案方向 |
|---|---|---|---|
| 1 | 时间平移 | 中 | 计算前曲内容终点（PPQ ticks），后曲全部时间字段整体 +T：音频/MIDI 事件、automation、marker、tempo/signature 事件、循环区间。字段名已知（`Start/Length/Bar/Position`），单位待 POC 确认（XML 时代为 PPQ） |
| 2 | 结构对齐 | 低（已统一） | 按轨道名对齐两工程轨道表；用标记计数先做"结构指纹"校验，不一致的工程拒绝合并并指名 |
| 3 | tempo/拍号拼接 | 中 | 两工程各有独立 tempo/signature 事件表，后曲事件平移 T 后并入；接缝处取后曲首个事件 |
| 4 | ID 冲突（RuntimeID/UID/GUID/IDLink） | 中（XML 输出时变低） | XML 输出路线下由生成器统一重排，结构完全受控；二进制路线需逆向引用图 |
| 5 | 媒体文件 | 中 | 各工程 Audio 目录 → 合并工程目录；重写剪辑引用路径（路径+GUID 双写保留）；按引用收集拷贝而非整目录 |
| 6 | 采样率不一致 | 低 | v1 直接拒绝并报明细（Cubase 对不匹配文件会变速变调）；你的工程同机同卡，实际大概率全 48k |
| 7 | 曲间 gap | 低 | 用户设定（秒/小节），换算成 ticks |
| 8 | 视图态/选择态等杂项节点 | 低 | 未知节点按长度跳过（自描述格式支持），靠 Cubase 加载端重建 |
| 9 | 插件状态 | 低 | 原样携带（二进制 blob 不解读不修改）——合并是"搬"不是"改" |

## 五、路线对比与推荐

| 路线 | 做法 | 优点 | 缺点/风险 |
|---|---|---|---|
| **A. 全二进制读写** | 逆向 RIF2，直接产出 C15 二进制 | 全自动、单文件产物 | 写入器风险最高：未知校验、CmIDLink 一致性、版本演进无人兜底；无社区先例 |
| **E. 读逆向 + XML 输出（推荐）** | 只读逆向 RIF2 提取内容模型 → 生成 ≤C12 XML .cpr → 用户 C15 打开（官方兼容）→ 另存 | 写端工作量降一个量级；格式合法性由 Cubase 加载器验收；XML 时代格式社区理解深 | 首次要"打开+另存"一步（可用本软件 GAKS 自动化代劳）；C15 对旧 XML 的兼容面需实测（POC 第一闸门） |
| C. GUI 自动化 | 用 GAKS 驱动 C15 内建"文件→导入→轨道来自工程"（可导入到光标位置，支持 tempo/markers 选项） | 零格式逆向 | 脆弱：对话框焦点/文案依赖、C15 有"导入后事件为空"的已知 bug 报告；批次大量工程时慢且不可靠 |
| D. AAF 交换 | 各工程导出 AAF → 合并 AAF → 导回 | AAF 是公开标准（有现成解析库） | 丢插件、自动化、MIDI 细节；两次导入导出人工环节 |

**推荐 E 为主线**，C 作为 E 的验证期人工兜底，A 作为 E 失败时的回退（读端逆向成果全部复用）。

现有替代品（说明自研价值）：Cubase Show Page / VST Live 是"多工程切换"而非"单工程拼接"，切换有加载间隙；手工 Import Tracks 是社区通行做法但纯手工。合并工程与本软件的定位点（GOTO）体系是天作之合：**合并完成即自动按歌曲边界生成定位点，演出时 MMC GOTO 跳曲**——这是外部工具给不了的闭环。

## 六、风险与未知项

1. **XML 兼容面（最大未知）**：C15 独有的新字段/新插件参数在 ≤C12 XML 模型里是否有落点。缓解：XML 的 `version` 属性与开放属性数组结构给了弹性；POC 用真实工程全量验证，失败才回退 A。
2. **时间单位与字段语义**：PPQ 值、tempo 的 µs/quarter 表示等，需 POC 对照（可拿一个 C15 工程的内容与 DAW 内显示的时值交叉验证）。
3. **格式演进**：Steinberg 更新可能改节点流。缓解：工具记录源文件 AppVersion，只承诺已验证版本；读端对未知节点跳过的容错设计天然抗演进。
4. **超大文件**：Steinberg 官方公告过 >2GB .cpr 损坏 bug（2024-02）。合并工程只拼引用不并音频，.cpr 本体不会大，风险低，但产物大小要有告警阈值。
5. **马虎产物损坏用户工程**：合并只读源文件、产物写到新目录，源永不改写——作为铁律写进实现。

## 七、POC 里程碑（建议顺序）

- **P0（1~2 天）节点树探针**：只读解析 C15 模板 + 2 个统一工程，还原 NUNDROOT 节点树（类名/字段/值），确认节点头布局（长度/名字/类型标记）与"未知节点可安全跳过"；交叉验证两工程轨道名序列与模板逐轨一致。
- **P1（约 1 周）最小读模型**：轨道表、音频/MIDI 事件位置、tempo/signature、marker、媒体引用的提取器；对全部 63 个工程批量跑通（健壮性即正确性证据）。
- **P2（约 1 周）XML 生成器 v0**：两工程拼接产物 + 真机 C15 打开验证（核对清单：时长、轨道内容位置、插件在位、automation 生效、无报错弹窗）。**这是全计划的 go/no-go 闸门。**
- **P3（约 1 周）产品化**：多工程批拼、gap 策略、媒体拷贝、采样率校验、定位点自动生成、软件内 UI 集成。

## 八、第二轮探针实证（语法主干已解明）

探针（`out/probe_cpr_{census,grammar,scan,fields,lib,map,diff}.py`，全部只读）：

### 8.1 容器与术语层（已解明）

- 容器：`RIF2` + u64 大端 size + `NUNDROOT`（C13 的 RIFX 为 u32 大端 size + `RIFF` 头）；节点流紧随其后。头部 ~600 字节为 AppVersion 固定格式元数据块（Cubase/版本/日期/WIN64/UTF-8/zh + `ROOT` 标记），可直接整块照抄。
- **术语记录**：`[BE32 长度=strlen+1][名字\0]`，单文件验证 20221 次；部分术语在 `\0` 后带 3 字节 UTF-8 BOM（`EF BB BF`，长度把 BOM 计入）——即首轮 dump 中"锘"乱码的来源。
- **值标签**（紧跟术语后，u16 大端）：`1`=i32(4B)｜`2`=列表（[u16 版本][BE32 数量] × (术语+值)）｜`3`=数据块（[BE32 尺寸][字节]——`MTempoTrackEvent` 的 370 字节块精确落到下一节点边界，已实证）｜`4`=f64(8B 大端)｜`8`=字符串（[BE32 长度][字节]）。
- **对象头**：术语后 `[u16 0]` + 8 字节头 + 子节点。实测两种形态：紧凑单子（`GDocument→CmObject→PArrangement`、`MGroupEvent→MPartEvent→MEvent→CmIDLink` 四级链全走通）与"哈希+数量"多子形态。

### 8.2 语义层实测（拍号/定位条/轨道/媒体）

- **拍号事件**（`MTimeSignatureEvent`）字段裸值已直接读出：`Flags=0、Start=0.0(f64)、Length=1.0(f64)、Bar=0、Numerator=4、Denominator=4`——与 C13 头部 dump 的字段名清单逐一对应。字段间尚有 4 字节间歇标记未定性（POC 项）。
- **速度事件**：`MTempoTrackEvent` = 标签 3 数据块（SOUL SOLDIER 370 字节，起止边界精确）；块内为打包浮点序列，内部编码留 POC。文件尾部亦有 `Type/flags/float=120.0` 的速度字段组（标签 1/1/4）。
- **轨道结构**：全库 86 工程的轨道类术语序列分布——**54 个 = Folder>Automation>Audio>Midi（模板全序）、29 个 = Folder>Automation>Audio、2 个多 InstrumentTrack、1 个乱序**；59/86 与模板逐类一致，"同名轨道顺延"前提成立。轨道类术语每工程恰 1 个（grep 重复计数是 `MAudioTrack ⊂ MAudioTrackEvent` 子串假象）。
- **循环定位条**：cpr_meta 的已证语法继续有效；**4 首歌内容先于左定位条**（アイドル 73.7s、Bad Apple!! 76.5s、SOUL SOLDIER 54.4s、平行線 32.9s）——合并平移必须以内容边界为准，不能以定位条为界。
- **媒体引用**：全库 574 条引用指向工程目录之外（大量在 `Downloads`）——**合并工程必须拷贝媒体入自己的 Audio 目录**，否则外部目录一清理即断链。单文件最多 29 条引用（东方组曲）。
- **媒体属性记录**（池尾）：`StMedia::PStringIDMediaAttribute` 类名 + `ID/Type/Flags/String/Long/Float` 字段组完整可读（如 ID="AudioSampleRate"、Float=54324.0）。

### 8.3 仍待 POC 收尾的语法长尾（已精确定位，非风险项）

MIDI 事件区独立编码（`MEvent/CmIDLink` 链）、字段间 4 字节间歇标记、标签 5/6/7 语义、速度块内部格式、事件 Start/Length 的成批提取（与拍号字段同机制）。这些是"一周量级的收尾"，不是可行性问题——主干语法族（术语+标签+对象嵌套）已在数十个独立样本点上一致。

### 8.4 社区先例补充

- [torkolycsaba/cubase-track-exporter](https://github.com/torkolycsaba/cubase-track-exporter)：第三方对二进制 .cpr 做签名扫描提取轨道名——与现代二进制格式打交道的公开先例。
- Plugin Bouncer（[note.com 文章](https://note.com/zap_akky/n/n2426fd8165fa)）：按 XML 文本解析旧版 .cpr 清理插件表——XML 时代格式可程序化编辑的实证。
- 本机 `cpr_meta.py` 本身就是格式可逆向的活证据（定位条读取 65/70 工程全中）。

## 九、模板样式核查与拼合操作规律（第三轮探针）

探针补充：`out/probe_cpr_map.py`（结构映射）、`out/probe_cpr_diff.py`（模板-工程字节一致性）。核查对象：新模板（10-27 12:42 重存，701KB，残留媒体已清）+ SOUL SOLDIER / Snow halation / Fly Me To The Moon 三个已统一工程。

### 9.1 骨架-内容二分（实测成立）

- **模板 64B 窗口逐字命中率 79%~81%**（每 512B 采样 1370 窗，三工程一致）：AppVersion 序言、文档链、通道/插件架构（**含 GUID 与插件状态二进制**）、FX 通道全部与工程字节级相同——工程确实是模板派生。
- 错位窗口（285 个）归因全部落在**会话态字段**：RuntimeID(53)/SlotType(21)/State(18)/QCDestinationValue(15)/BypassTag/OldOn/"---"/Bay Program…——Cubase 每次会话重建的运行时数值，不是结构差异。
- 工程独有内容（44%~53%）= 轨道事件与音频事件链、媒体路径/OrigPath、拍号事件数量（模板 1 个、SOUL SOLDIER 6 个）、速度块、**歌内自加轨道**（SS 的 Audio 13/14）、剪辑名字符串。
- **轨道名表**：模板与工程共有 `Audio 01~12`（对齐键成立）+ FX 通道 `vo effect 1/2` + `output/click/drummer/Mono`；歌曲附加轨按名追加。注意：现有工程对齐的是 10-22 版模板，当前模板 10-27 又演进过——**预检指纹必须对比"歌与歌"，不能对比"歌 vs 当前模板"**。

### 9.2 拼合操作规律（六条）

1. **骨架照抄模板**：AppVersion 块、文档链、轨道表结构、通道/插件架构（含 GUID 与插件状态）、FX 通道。会话态字段（RuntimeID 等）取模板值，由 Cubase 加载时重建。
2. **内容注入面**（来自各歌，全部平移 +T）：音频事件链 `MAudioTrackEvent→MAudioEvent→PMediaDescriptor→PAudioClip→MHitPointEvent→GridDef→MFade/MFadeIn/MFadeOut/MInterpolator`；MIDI 链 `MGroupEvent→MPartEvent→MEvent→CmIDLink`；速度块 `MTempoTrackEvent`（标签 3）；拍号 `MSignatureTrackEvent`+`MTimeSignatureEvent×N`；轨自动化。
3. **轨道对齐键 = 轨道名字符串**（`Name→String` 值），共有轨顺延、歌曲附加轨按名追加；预检指纹 = 歌间轨道名表 + FX 通道名 + 采样率 + 媒体在盘。
4. **媒体引用三件套**（绝对路径+GUID+OrigPath）→ 拷贝入合并工程 Audio/ 并重写路径，GUID 保留（文件身份不变）。
5. **系统数据表合并**：拍号/速度事件表平移拼接（数量随歌变）；`MTrackVariationCollection/CmArray` 等结构容器取模板。
6. **位置域双轨**：拍号 `Start/Length` 是 f64（小节域），事件位置在另一 tick 域——平移在各自域内进行，不做跨域换算（POC 定标）。

### 9.3 对设计案的影响

骨架-内容模型使 POC 的 writer 从"重建整个工程"降为"模板骨架 + 内容区重组"，工作量与风险进一步下降；预检指纹按 9.2 第 3 条修正。设计案 `docs/设计-合并工程.md` §2.2 已同步。
