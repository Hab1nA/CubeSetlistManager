# 舞台射频频段调研

> 日期：2026-10-02。背景：10-02 演出满场后三条无线链路（翻谱热点/蓝牙踩钉/MIDI-A/B）同时失效。
> 现状前提：**热点仍由本机内置网卡发出（Windows 移动热点，2.4GHz）**，尚未迁移旅行路由器。

---

## 一、本软件自身涉及的射频链路（现状盘点）

全部关键链路集中在 **2.4GHz ISM（2400–2483.5MHz，共 83.5MHz）**，且两条经过同一块硬件：

| # | 链路 | 技术 / 频段 | 射频路径 | 承载内容 | 关键等级 |
|---|------|------------|---------|---------|---------|
| 1 | 翻谱热点 | Windows 移动热点 = Wi-Fi Direct 软 AP（WinRT `NetworkOperatorTetheringManager`，`hotspot.py`），**2.4GHz** | **内置 combo 网卡**（STA+AP 同 radio） | 平板浏览器 REST：1 秒轮询 + POST 命令（谱面/歌单/走带/翻谱） | 演出关键 |
| 2 | 蓝牙踩钉 | BT Classic HID 多媒体键（M-Vave CUBE TURNER PRO），2.4GHz AFH 自适应跳频（79×1MHz 信道） | **同一张内置 combo 网卡**收（Raw Input 路径） | 走带控制（暂停/开始/回零/全停/上下首） | 演出关键 |
| 3 | MIDI-A/B 无线 MIDI 盒 | 2.4GHz **私有跳频协议**（非 WiFi、非 BT，占用方式不透明、无法协调） | 盒对盒空中链路，经 USB 进 PC | 键盘/延音 CC → loopMIDI → midi_bridge.py / Cubase 触发轨（config 口名 "JUNO"） | 演出关键 |

伴生角色：若演出时 PC 还连着场馆 WiFi（STA），同一张网卡同时扮演 **STA + 软 AP + BT 主控**三个角色；热点要求"先连任意网络"（`hotspot.py` 逻辑），所以 STA 角色几乎必然在场。

流量特征：1 秒轮询 = 常载小包流量（对丢包敏感度低，掉一拍下一拍补上）；POST 翻谱命令 = **事件型、无重试，丢一次=漏翻一页**。

## 三、冲突矩阵（本软件三链路 × 舞台常见设备）

| 舞台设备 | 频段 | vs 翻谱热点(2.4G) | vs 蓝牙踩钉(2.4G) | vs MIDI-A/B(2.4G) |
|---------|------|------|------|------|
| UHF/VHF 话筒、UHF 耳返 | 470–788MHz | 无冲突 | 无冲突 | 无冲突 |
| DECT 内通 | 1.9GHz | 无冲突 | 无冲突 | 无冲突 |
| 观众 WiFi + BT | 2.4GHz | **强冲突**（数百终端扫描+流量，CCA 全忙） | **强冲突**（AFH 只能避让，避不动就牺牲吞吐） | **强冲突**（私有跳频在最拥挤段） |
| 无线吉他系统 | 2.4GHz | **强冲突**（发射机在台上 0.5–2m 近场，信号强） | 强冲突 | 强冲突 |
| 无线 DMX（CRMX/W-DMX） | 2.4GHz | **强冲突**（认知跳频+灯具在桁架高处=全场视线覆盖） | 强冲突 | 强冲突 |
| 2.4G 数字话筒/耳返 | 2.4GHz | 冲突 | 冲突 | 冲突 |
| 图传（双频款如 Mars） | 2.4+5GHz | 部分冲突（若图传落 2.4 档） | 部分冲突 | 部分冲突 |
| 5GHz WiFi / 5.8G 图传 | 5.xGHz | 无冲突（现状）；**若热点迁 5GHz 则同频，需定频避开图传** | 同左（若 BT 仍 2.4 则无冲突） | 无冲突 |

结构性问题：2.4GHz 只有 **3 个不重叠 20MHz 信道（1/6/11）**；本软件三条链路 + 舞台上所有 2.4G 设备都挤这 83.5MHz；BT 的 AFH、CRMX 的认知跳频、MIDI 盒的私有跳频**三方互相"尽力而为"，没有任何协调机制**。

## 四、稳定性评价（当前 2.4GHz 机内热点配置）

**实证：10-02 满场全灭（空场彩排三条链路全绿）——已经不是理论推演。** 三个机理叠加，缺一不至于全灭：

1. **频段拥挤**：满场后观众数百台 WiFi/BT + 会场 2.4G 设备把 83.5MHz 塞满，CCA 退避 → 轮询 RTT 秒级抖动、POST 丢包=漏翻页。
2. **人体吸波**：2.4GHz 是水吸收峰（微波炉 2.45GHz 同段），密集人墙 10–30dB 衰减 + 多径抖动；机内天线在桌面高度，翻谱平板在台上——信号全程穿人。
3. **combo 网卡内部饿死（架构耦合）**：软 AP 与蓝牙跑在同一块芯片，802.15.2 共存仲裁在热点信道被打满后直接牺牲 BT 时间片——**即使场外干扰为零这条也存在**，踩钉失效一半是内部问题。

逐链路评级（当前配置、演出场景）：

| 链路 | 评级 | 主失效模式 |
|------|------|-----------|
| 翻谱热点（机内 2.4G） | **差——不可用于演出关键链路** | 拥挤+人墙衰减+与 BT 内部竞争；POST 丢=漏翻页 |
| 蓝牙踩钉 | **差** | 场外拥挤 + 同卡被热点饿死（双因素，后者与人数无关） |
| MIDI-A/B 盒 | **差** | 私有跳频无协调手段，最拥挤段最脆弱 |

**结论：换信道、加功率、调路由器设置都救不了 2.4GHz**——拥挤、吸波、内部饿死三条没有一条是软件或频率规划可解的。当前配置的稳定性是"观众人数的函数"，演出场景不可接受。

## 六、两个候选改善方案评估（10-02 追问）

前提：舞台布局=PC 离踩钉较远，平板与踩钉相距约 1m。

### 方案 1：踩钉改连平板 —— 不建议

BT 跳数本身确实变扎实（1m 近场 HID 低速率+AFH 几乎打不死，且脱离 PC combo 卡、内部饿死不再波及踩钉），但系统层面是退步：

1. **功能错位**：踩钉是走带控制器（六动作控 DAW），不是翻谱器。配对到平板后，媒体键只能被谱面 App 收去做翻页（这部分零开发可用）；六动作要到达 PC 必须由 Cube Remote APP 新增「媒体键接收 → HTTP 转发 → 单/双踩时间窗消歧」——安卓端开发项目。
2. **失效域合并**：现状踩钉（BT）与显示（WiFi）是两条独立路径，热点死踩钉仍活；改成踩钉→平板→PC 后全挂在平板↔PC WiFi 一跳上——热点一死，翻谱显示和走带控制一起灭。10-02 那种场面下此配置死得更彻底。
3. **BT 单配对**：踩钉一次只能配一台主机，临时切回 PC 要重新配对，台上没有切换能力。

踩钉链路的固化走既有 P0（有线 USB HID 脚踏）或 P1（Class 1 dongle）更干净。方案 1 唯一适用场景：热点全灭时的保底手动翻谱——但受限于单配对无法与 PC 同时在线，实用价值低。

### 方案 2：WiFi 6 外置网卡（6dBi 天线）做热点源 —— 有效，建议做

三个机理打分：

| 失效机理 | 效果 | 说明 |
|---------|------|------|
| 内部饿死 | **根除** | SoftAP 移到 USB 专用卡，内置卡只留 BT；建议顺手禁用内置卡 WiFi，消除残余共存仲裁 |
| 频段拥挤 | **大改善** | WiFi 6 卡必双频，Win11 热点属性「网络频段」选 5GHz：>20 个不重叠信道，观众干扰密度比 2.4GHz 低一个量级 |
| 人体吸波 | 部分补偿 | 6dBi 对机内天线实测增益约 +3–4dB，10–30dB 人墙衰减靠天线增益赢不回来；**胜负手是 USB 延长线把天线架高至人群上方+视线可达**。注意 5GHz 人体吸收比 2.4GHz 更高——架高从可选变必选 |

三个坑：
1. **SoftAP 支持**：不是所有 USB 网卡 AP 模式稳定。买前确认芯片主流 SoftAP 支持（MT7921AU / RTL8832BU 一类较稳），到手即测：开热点→频段选 5GHz→平板连上跑全套。
2. **Tethering 前提**：Windows 移动热点要求 PC 已连某网络才可开启（`hotspot.py` 报错文案即此）；现场走网线或新卡 STA 均可满足。另外 `hotspot.py` 取第一个具热点能力的 profile，双 WiFi 卡并存时选中谁不保证——禁用内置卡 WiFi 一步解决（否则可能要给脚本加优先外置卡）。
3. **WiFi 6 协议本身不是得分点**：平板单客户端，OFDMA/TWT 意义很小；得分靠频段+天线位置+解耦，别为 WiFi 6 标签加钱。

信道：定频 149/165 高段（非 DFS、平板兼容性最好），留意与 5.8G 图传可能同段，现场换信道实测。

**定性**：此方案≈P0 旅行路由器方案的「免软件近似版」（5GHz 专用 AP + 蓝牙解耦 + 外置天线）。旅行路由器仍是金标准——AP 可独立架高、定频自由、隐藏 SSID、不占 PC 的 USB 口和驱动稳定性；USB 网卡方案的主要不确定性在驱动 SoftAP 质量。

### 结论

先做方案 2；踩钉不连平板，按 P0 有线化推进。

## 七、踩钉冗余路：有线连平板 + APP 转发（10-02 追问二）

> 诉求：BT 直连 PC 保持不变，另加一路——踏板用线连平板（平板距踩钉约 1m；连 PC 不现实，走带 4–5m 线缆穿台），平板 APP 经 WiFi 转发给 PC。

### 前提修正与部署形态

TurnerPro 没有可用的有线模式（10-01 实测 6.5 转 USB 枚举为假「EarPods」，零有效输入）。故此路落地形态必然是**第二只踏板**：一只廉价有线 USB HID 脚踏常驻插平板（USB-C OTG），TurnerPro 继续蓝牙连 PC。"保持蓝牙不变"由此自然成立，两脚两路、无需配对切换。

零软件对照版：USB 2.0 无源线 5m 内在规范边缘（低速设备标称 3m，5m 实测多可用，¥20 有源延长线保底），¥50 踏板直插 PC 即得同等失效域解耦、零开发——台面布线能接受时这仍是最省方案；不能接受再走平板转发。

### 方案是否成立：成立，定位=冗余路而非替代路

| 失效机理 | 效果 |
|---------|------|
| 2.4GHz 拥挤/吸波 | **第一跳出局**：踩钉→平板从最脆弱的射频跳变为 1m 线缆；后续平板→PC 走 WiFi |
| 失效域解耦 | BT 路死于 2.4GHz 拥挤+吸波时，平板路走 1m 线+WiFi 仍活——**前提是方案 2 落地**（WiFi 已迁 5GHz 外置卡）；若 WiFi 仍是 2.4GHz 机内热点，10-02 实测两路会同灭，冗余不成立 |
| 新增依赖 | 平板成为该路单点（死机/没电=此路灭，BT 路仍在）；需安卓端开发；网络注入输入=信任边界（与命令通道同级别，默认关闭+开关） |

实施顺序：先方案 2，再本方案。

### 两个技术分叉：选 B（原样转发、PC 统一识别）

**分叉 A（APP 本地翻译成语义命令，走 UI 按钮同款通道）的问题：**
1. 语义重复实现且必然漂移：单/双踩时间窗、双锚 30ms 弹跳闸、temporal 键、三态 play/pause toggle（stopped 拦截）——引擎历史修复极多，安卓端全要复刻一份，此后每次引擎修 bug 都要双写。
2. 学习功能无法覆盖：PC 侧 Learner 绑定的是 VK，翻译路永远不产生 VK，得在平板再造一套绑定 UI/配置——一套踏板两套配置。
3. 三态 toggle 依赖 PC 实时播放态，APP 只有 1 秒陈旧态，有竞态。

**分叉 B（转发原始输入，PC 视同蓝牙输入）的设计要点：**
1. **转发内容**：不转 Android keycode，转 **HID usage（`KeyEvent.getScanCode()`）+ down/up 边沿 + APP 端单调时间戳**。同硬件同 usage，两条连接路键身份天然一致。
2. **PC 注入层**：在 `DeviceBridge._feed` 同层注入（`engine.feed(("hid", vk), down, now)`，与 Raw Input 汇合于同一命名空间）；PC 端补 LKC/AKC 双键码表（vk=scanCode 主查 + kc=keyCode 兜底，见第八节 P0 教训——scanCode 是 Linux 键码非 usage）。**蓝牙学的绑定对平板路自动生效**，temporal/去抖/三态/学习分流全部免费继承，PC 端改动极小。
3. **学习功能**：控制页学习流程不变——键身份一致，BT 学一次两路通用；若想让平板路本身也能学习（新踏板从未配过 PC），让学习态下 remote 注入事件同样进 `begin_capture` 回调即可，事件同层注入所以自动可达。
4. **时间戳重定基准**：APP 时间戳随包发送，PC 按包首事件 rebase——网络抖动不进 30ms 弹跳闸/0.35s 双踩窗，物理 7–16ms 脉冲不被 WiFi 抖动虚增。延迟预算几十 ms，走带控制无感。
5. **平板端捕获**：扩展现有 `TurnAccessibilityService` 加按键过滤（只拦踩钉键位：media 键/F13–F24），或 MediaSession 接管；转发跑在现有 `TurnService` 前台服务里（后台冻结免疫，无需新造组件）。**转发/透传模式开关**：转发档拦截键（键=走带语义），透传档放行给前台谱面 App 自己翻页——与 PC 端 intercept 开关对偶。
6. **多设备预留**：事件包带设备标签（VID/PID），对应 `hidDeviceHint` 的按设备绑定，未来双踩钉并存可区分。

### 结论

方案成立且有真实优势（第一跳有线化 + 与 BT 路失效域解耦），但**必须以方案 2 为前提**；两个分叉选 B，PC 端改动极小且学习功能免费复用。若台面能布 5m 有源 USB 线，零软件直插 PC 版更省，二者按布线条件二选一。

### 通道与语义（审查修复后）

- 采集：踏板 USB-C 线连平板 → 系统输入栈（标准 HID 键盘，无需 USB Host API）→ 无障碍 `onKeyEvent` 捕获（`flagRequestFilterKeyEvents`；键位白名单双域=keyCode 或 scanCode；转发/电脑端关闭时返回 false 放行给谱面 App=透传档；音量键在白名单外，平板音量控制不被吞）。
- **键码命名空间（第一轮审查的 P0 教训）**：`KeyEvent.getScanCode()` 上报的是 **Linux input.h 键码（LKC）**，不是原始 HID usage——内核 hid-input 层把 usage 折算成 LKC 再进 evdev，usage 不传给应用（AOSP《Keyboard devices》码表：Play/Pause 0xCD→LKC 164、Scan Next 0xB5→163、PageUp 0x4B→104）。协议双字段：`vk`=scanCode（LKC 主查表）+ `kc`=Android keycode（兜底表，个别栈 scanCode 报 0）；两表对同一物理键映射一致，**蓝牙学的 VK 绑定对转发路自动生效**。LKC 87=F11 与 AKC 87=下一曲同数值不同义——F 键/字母/数字区间映射严格按表作用域，绝不混用。
- 打包（`PedalBatcher` 纯类，JVM 可单测）：等 UP +40ms 静默窗；**分块 ≤32 条/跨度 ≤5000ms**（主线程卡顿积压时不整包报废）；`dt`=距块内**最大时戳**偏移（非末元素——迟到真实 up 不产生负 dt）；`repeat>0` 丢弃；DOWN 1s 未见 UP 补合成 up；打包逻辑 @Synchronized（捕获主线程/JS 桥线程/开关线程三方互斥）。
- 传输：`POST /pedal/event`，带 per-boot 随机 `sid`（会话标识）+ 单调 `seq`——同进程重发按 `(device, sid, seq)` 等值幂等确认，**进程重启 sid 换新即新会话**（seq 归 1 不会被旧基准静默吞掉——演出中途 APP 崩溃重启的第一脚是救场动作）；失败 200ms 重试，**包龄超 2s 丢弃** + Toast + /diag；**403=电脑端开关未开：按键透传谱面 App + Toast 提示，心跳照发——电脑端开回即自动恢复**（不再要求 APP 人工重开）；心跳 5s。
- 入站防护（新端点不扩散存量裸奔）：**私网来源门**（复用 valid_push_ip 规则，PC 误接场馆 WiFi 时 LAN 任意主机不得注入按键）+ 全局限流 40 包/秒兜底（per-device 20ms 桶可被设备名轮换绕过）+ device 去重表 32 席上限。
- 注入：`remote_key_to_vk(sc, kc)` → `DeviceBridge.inject` → `_feed` 同层（学习/控制页静音/单双踩分流零改动继承）；`_io_lock`（RLock）串行化桥线程 raw 路径与 HTTP 注入；远程 up 沿**不消费本地热键 `_pending`**（拦截开启时不合成从未发生的按压对）；跨源去重保险（同键 down 沿距本地蓝牙沿 <0.15s 丢弃远程份）。
- 时间基准：`dt` 保包内间距 + `et`（APP 单调时戳）跨包锚定（`RemoteClock`：按 APP 时差外推、trim 掉到达抖动、时戳回跳=重启自动重锚）——窗内间距不被网络拉伸、弹跳闸/去抖窗按真实间距判定。**能力边界（诚实声明）**：包到达晚于手势窗剩余时间时窗内定时器已触发，任何接收端无法回溯补救——蓝牙直连同款 RF 延迟同样劣化，锚定保证转发路不比直连更差（线级模拟 S17 钉死）。

### 开关与健康显示

- 电脑端：踩钉控制页「允许平板转发踩钉」勾选（`config.json["pedal"]["remoteEnabled"]`，默认关，读取对非 dict 配置防御）。
- 平板端：APP 设置面板「踩钉转发」开关（默认关）；**开启时自检无障碍 capabilities**——APK 升级后 flag 快照未刷新（OEM 行为不一）时当场弹窗引导关-开无障碍；面板文案注明升级后无反应的处理与透传行为。
- 健康显示：`/state` 快照 `pedalRemote = {enabled, link: never|ok|stale, unknown, lastEventAge}`；**未识别键丢弃计数**（`unknown`）与心跳独立——心跳只证链路活，unknown>0 说明键路不通（固件换键位/表缺键），状态行转警示色，防止「心跳买活绿灯掩盖按键全灭」。
