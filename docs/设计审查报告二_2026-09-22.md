## 总体结论

一轮改造把软件从"工程师的控制台"推进成了"演出者的控制台"：信息层级、防误触、深色可读性三大短板全部补上，且核验属实。但本轮渲染实测揪出一个 **P0 级界面缺陷：默认窗宽下「播放配置」组的 5 个控件（时长输入/写入时长/重新识别/设置）整体不可见**——这正是"莫名其妙的卡点"的典型形态。其余为少量残留直觉问题、两条稳定性纪律补丁和架构遗留。稳定性方面，通读未再发现会冻结界面的新路径；真机 exe 与源码同步，crash.log 已挂且为空。

## 一、P0：默认窗宽下「播放配置」关键控件整体不可见（几何实测）

**现象**（winfo 实测，非目测）：默认窗口 980×840 逻辑（175% DPI = 1715 物理px）下，
播放配置组只分到 282px；组内 pack 顺序在「配置目标跑马灯」之后的 **时长→标签、
时长输入框、写入时长、重新识别、设置** 五个控件宽度全为 1px，被 pack 完整裁剪——
控件不是禁用，是**消失**，且无任何视觉提示。拉宽到 1300 逻辑（2275 物理px）才全部可见；
minsize 940 下同样全灭。

**为什么至今没暴露**：平时最大化/宽屏使用（≥1300 逻辑宽就正常）。但只要一次非最大化运行
（默认 geometry 就是 980！），「手填时长」（怪物/TAIDADA 等 5 首未知时长曲目的唯一兜底）
和「设置」入口就凭空蒸发——用户会以为软件坏了。这比任何 bug 都符合"莫名其妙的卡点"定义。

**根因**：底部一行塞了编排/播放/自动化/播放配置四组加退出，总需求宽度超出窗宽；
播放配置组内部又是弹性控件（配置目标 Marquee，expand=True）先 pack、固定控件后 pack——
pack 空间不足时按顺序裁剪后排。

**修复方向**（任选其一，推荐 1）：
1. **底部控制条两行化**：第一行=编排+播放+自动化+退出（演出中要按的全在一行，宽度绰绰
   有余）；第二行=播放配置独占一行（fill=x）。窗口纵向有富余——日志栏下方实测约 40%
   高度空置，正是可让出的空间。
2. **减负**：删「配置目标」标签（选中态与 NOW 横幅已表达此信息）、
   「清空播放列表」→「清空」、播放组按钮 width 5→4，合计省约 400px。
3. 无论选哪个：**关键固定控件必须 pack 在弹性控件之前**——空间不足时先牺牲跑马灯。

## 二、功能逻辑 vs 用户直觉（残留问题）

1. **双击切歌确认依赖时钟存在**：确认条件是 `watch.is_transport_live()`，它只在收到过
   MIDI 时钟后才可能为真。库内大量工程不发时钟（实测仅 9 个工程引用 loopMIDI）——
   对这些工程，双击即切、无任何闸门，而"不知道在不在播"的工程恰恰是最容易误判的场景。
   建议：`i != self.cur` 即确认（成本=有意切换多点一次），或设置页加"双击切换需确认"默认开。
2. **切换进行中可点退出**：ctrl.busy 时退出，GUI 销毁但切歌线程（daemon）还在跑，
   会继续向 Cubase 发键、放行弹窗——半途而废的自动化比不自动更难收拾。建议退出路径
   检查 busy：提示"正在切换工程，确定退出？"
3. **无时钟工程零时间信息**：剩余时间只在 is_following 时显示，无时钟工程连总时长都
   不显示。小改：无时钟时静态显示总时长（数据已有）。
4. **panic 缺全局热键**：屏幕按钮已有，但演出中焦点可能在 Cubase/他处。
   `RegisterHotKey`（如 Ctrl+Alt+S）是不依赖焦点的最后保险，标准库 ctypes 可做。
5. **排序仍逐格上移/下移**：多选加入已大幅缓解编排量，拖拽排序（Listbox 单行绑定可做）
   维持 P2 可接受，不阻塞。

做得好的（本轮再确认）：无工程按「开始」自动加载当前项再播、busy 时手动请求排队、
双击当前项不重载、移除当前项指针顺移、重启按窗口标题恢复当前工程——边界行为都有交代。

## 三、UI 设计现状（渲染实测）

**成立的部分**：上下分区逻辑清晰（数据→监控→日志→控制）；NOW/NEXT/剩余时间层级正确；
监控栏两栏同构、绿黄红语义色贯穿列表三态与状态格；底部四组等高；深色下发亮的绿色「开始」
和红色「全停」有恰当的视觉权重。**美观度从一轮的"未设计"（50 分）提升到约 75 分**，
剩下的是打磨不是缺设计。

**问题清单**（除 P0 外按影响排序）：
1. **日志栏空置**：与双列表共享伸展空间，行数少时下方大片空黑（截图实测约 40% 高度）。
   日志固定高度（6-7 行不伸展），伸展让给列表，顺便为 P0 的两行化腾出高度。
2. **列表行超宽硬裁无省略号**：长歌名在列边界被拦腰截断（实测"(Explicit) ·（自动时"
   戛然而止），无"…"提示有省略。用户已明确列表不做跑马灯，那至少做字符截断+省略号。
3. **禁用按钮 affordance 偏弱**：darkify 未显式设 disabledforeground（现为
   SystemDisabledText）。像素实测：禁用文字峰值亮度 109 vs 可用 227（底色 30）——
   能分辨，但暗场远距下偏弱。显式设 #6a6f76 一类中灰并统一。
4. **「自动时长」文字噪音**：播放列表每行都缀"（自动时长）"，颜色已传达三态，自动态
   可不显文字（或显示数值），每行省 6 字符的噪音，长歌名也能多显示一截。
5. **键盘自动化窗口过宽**：760 逻辑宽（1330px），内容实际 ~500px 宽，映射列被拉出
   大片空白、按钮顶到右缘。缩到 ~560 更紧凑。
6. **设置页中部留白**：420 逻辑高只用了一半，可收紧到 ~340。
7. 无程序图标：任务栏/标题栏是 Windows 默认图标，演出环境投屏露脸。iconbitmap 一行事。

## 四、技术栈与稳定性（演出软件视角）

**框架结论维持**：tkinter + 纯标准库 + onedir 是正确选择。真正的天花板在"对 Cubase 的
控制是 UI 自动化"（窗口标题/仿人键/前台焦点），换任何前端栈都不会更好；本机
python-rtmidi import 即崩的教训也证明依赖面越小越稳。不换栈。

**本轮通读新发现**（按优先级）：
1. **启动仍有"一票否决"残留**：`_startup` 里端口创建已逐项降级，但 `ObsController(cfg["obs"])`
   （config 缺 obs 段即 KeyError）、AdvanceWatch、**CubaseController 的创建仍在同一个
   try 里**——任何一个构造异常，后面全部不创建：GUI 活着但切歌/走带/全停全废，只有
   日志一行红字。建议每个服务对象独立 try/except（对齐端口已有的降级纪律）。
2. **`_transport` 的"自动加载"分支存在后台线程摸 Tk 的路径**：`_auto_play` 在后台线程
   调 `_transport`；若那一刻 `current_project()` 恰为 None（窗口枚举瞬时失败），会从
   后台线程走进 `_switch` → 直接 `_refresh()` 操作 Tk 控件。这是全代码唯一违反
   "Tk 单线程"纪律的路径，概率低但存在。建议该分支经 `calls` 队列送回主线程执行。
3. **VJ 进程隔离未做（一轮 P2 遗留）**：单进程全家桶意味着 Cube Setlist Manager 崩溃=视频/音色联动
   同时失联。现有降级已很好（重启恢复当前工程/时长/映射、OBS 自动重连、踩钉热插拔、
   crash.log 尸检），但"死而不倒"只有进程隔离能给出。评估项：Cubase 时钟目的地改指
   第二个 loopMIDI 端口、VJ 链路交回独立 VJ Automator.exe。保持 P2，演出压力前值得做。
4. 小项：crash.log 只 append 无轮转（长期会涨）；踩钉「学习」监听所有空闲输入口，
   JUNO MIDI IN 也在候选内——琴上弹 CC 会误绑（学习时排除已知 JUNO 名或界面提示）。

**"绝不卡死"审计结果**：`_tick`/`_watch` 双护栏、winmm 回调只记账、ToneSwitcher 串行
线程、OBS 动作永不抛、`_atomic_write`+损坏降级、切换全程超时上限（关 30s/开 120s）、
弹窗放行补发只补一次——**本轮通读未再发现会冻结界面的路径**。一轮发现的
"轮询死一次=界面假死"类风险已被系统性消除（try/except + 必重排 after）。
